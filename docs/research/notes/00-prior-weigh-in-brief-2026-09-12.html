Section 1 · This is what a Weigh-In item looks like

The decision on the table

Rather than describe the tool, the tool's core question is presented below in the format the research argues for: a full interrogative, why it matters, the door type, evidence you can verify, options that each get a steelman, and a recommendation you have to ask for. Read the options first — the recommendation is behind a reveal on purpose (see principle 6).

D-0001 presented one-way door blast radius: every repo you run agents in resolve by: before Phase 1 build
What shape should the human-in-the-loop decision-review mechanism take — adopt, skill pack, plugin, Redkiln-native item type, or standalone SDK console?

Why it matters. The shape fixes where captured items live, whether capture can run unattended, what the review surface can look like, and whether decisions flow back into .kb. Reversing it later means migrating a register and retraining habits — the evidence says a decision practice survives on habits, not on markdown.

Considered options
A

Adopt existing pieces as-is

effort: hours

Install spec-kit's /speckit.clarify, compound-engineering's ce-plan, and adr-gen's Stop hook. Use their spec-local Clarifications sections and post-hoc ADR generation.

Good, because

  • spec-kit's question format is the best-specified in the field: impact×uncertainty ranking, ≤5 per session, recommendation with reason, deferred list, write-back with contradiction removal
  • Zero code to maintain

Bad, because

  • Everything is spec-local or plan-local — no register, no status, no owner, no expiry
  • Nothing captures from console output or finished artifacts
  • adr-gen parses transcript JSONL that Anthropic says changes between versions; 1-star, single author
  • No grounding against .kb; no UI beyond chat
Strongest case forIf most of your sessions are interactive and single-repo, clarify-before-plan removes the majority of buried questions at their source, and the "register" you'd build might become archaeology.
grounded in: spec-kit clarify.md · ce-plan SKILL.md · adr-gen README · sessions doc
B

A skill pack, prompts only

effort: a day

/hitl-scan (extract from a path or the current session), /decide (walk items with AskUserQuestion), /record (write a MADR record). Lives in .claude/skills or a plugin's skills/.

Good, because

  • Fast; no infrastructure; works in every repo the moment it's copied in
  • Question cards are native (1–4 questions × 2–4 options, "(Recommended)" first, previews in the SDK)

Bad, because

  • Nothing is always-on: items are found only when you remember to run the scan
  • Ambig-SWE: agents merely told to ask over-ask and lose accuracy on well-specified work — triage needs to be a separate pass, which prompts alone don't enforce
  • Presentation capped at four options per question; no evidence links, no metrics, no "not useful" loop
Strongest case forEvery larger option contains B as its first slice. Building B first and measuring how many items are actually acted on is the cheapest way to learn whether a register earns its keep.
grounded in: skills doc · SDK user-input doc · Vijayvargiya et al. ICLR 2026
C

A Claude Code plugin with hooks, agents and a registry server

effort: weeks, in slices

Skills from B, plus Stop/SubagentStop/PostToolUse capture hooks (prompt-type classifier), triage and grounding subagents, and a small MCP server that owns the register (SQLite or JSONL), serves a local review page, and writes ADRs back.

Good, because

  • Always-on capture without changing how you work; portable across every repo via a marketplace
  • The register gets the three things the evidence says keep a practice alive: owner, trigger, expiry — plus action-rate metrics
  • Review surface is unconstrained (evidence links, reversibility badge, reveal-on-demand recommendation) via URL-mode elicitation or a Cowork artifact
  • Plugins can also carry monitors/, output styles and settings, so the "Needs you" nudge can be a background monitor

Bad, because

  • An MCP server is a process to keep alive and version
  • URL-mode elicitation is documented with authentication as the example; using it for a review page is plausible but unproven
  • Register lives beside Redkiln's backlog rather than in it — two sources of "what needs a human"
Strongest case forC is the portable core: it works in IQBG client repos that will never run Redkiln, and D can be layered on where Redkiln exists. Portability is the only way the habit forms everywhere.
grounded in: plugins-reference · hooks doc (prompt hooks, Elicitation) · Tricorder 2018 · SATD literature
D

Redkiln-native: decision as a first-class item type

effort: weeks, on top of C

Add decision beside bug / incident / spike, with its own process (captured → triaged → grounded → presented → decided → recorded). The CLI keeps the single write path; the plugin from C is the capture/ground/present layer; the record lands as a .kb decision atom through kb-ingest; the Companion dashboard gains a "Needs you" column.

Good, because

  • Decisions become backlog items with the same stamped frontmatter, owner and stage as everything else — queryable with redkiln status, not a side file
  • Fits conventions already in force: accepted ADRs in .kb, supersede-never-edit, adversarial review gate before "decided"
  • Closes the loop the literature says is missing: question → human answer → durable record with neglected alternatives → constraint on future agents

Bad, because

  • Couples the mechanism to Redkiln's process engine; churn there is churn here
  • Non-Redkiln repos get nothing unless C ships as the portable core underneath
  • Largest total effort; the item type touches CLI, schema, and dashboard
Strongest case forYou already own a backlog engine with a knowledge base, an intake pipeline and a review gate. A HITL decision is an item type you haven't declared yet, not a new system.
grounded in: redkiln conventions (hierarchy, single-write-path) · kb-ingest and closeout skills · Buchgeher 2023 · Kaplan-Moss on RFCs
E

A standalone SDK review console

effort: weeks

A Python Agent SDK app that runs agents itself, intercepts AskUserQuestion in canUseTool, uses defer to park questions from headless and workflow runs, and presents an inbox web UI. Interactive terminal sessions would not route through it.

Good, because

  • Only path that serves unattended runs, cron'd tasks and workflows, where nobody is at the terminal when the question is raised
  • Complete UI freedom; HTML option previews are already an SDK feature

Bad, because

  • Duplicates Claude Code's own session UI for the interactive case
  • defer only works when Claude makes a single tool call in the turn, and only under -p
  • Most engineering, and it changes how you launch agents
Strongest case forYour stated direction is "permanently hosted, reusable agents" serving multiple endeavors. In that world nobody is at a terminal, and the defer loop is the whole mechanism.
grounded in: hooks doc (defer) · SDK user-input doc · headless doc
Reveal the recommendationhidden until you've read the options — it's a forcing function, not a trick

Recommended: D, built as C, with E's defer loop as a later slice. Make decision a Redkiln item type as the destination, but build the capture, grounding and presentation as a portable plugin so that IQBG client repos and anything outside Redkiln get the same mechanism. Ship B's skills as the first slice of that plugin, adopt spec-kit's question rules and MADR 4 wholesale instead of inventing formats, and add the SDK defer loop only when headless runs start generating questions nobody sees.

The reasoning is about long-term survival, not features. Three things decide whether a decision practice is still alive in a year: every item has an owner and an expiry, the answer is written where the code lives at the moment of action, and someone measures whether items were acted on. A and B provide none of the three by themselves. C provides all three but leaves decisions outside your backlog. D puts them inside it, which is where your other hard-won process rules (single write path, review gates, kb intake) already apply. E is the right answer for a future you have described but not yet built.

Why this might be wrongIf eight in ten of your agent sessions are interactive and single-repo, A+B captures most of the value in a day, and the register would be maintained at the cost of the very attention it's meant to save. The Redkiln coupling also bets that the process engine is stable; if it's still moving weekly, hold D and let C run alone for a quarter. Finally, URL-mode elicitation is documented for auth flows — if it's clumsy as a review-page launcher, the fallback is AskUserQuestion cards plus a read-only review page, which is less interactive than you asked for.
Pre-mortem · it's March 2027 and Weigh-In is dead — why?The classifier hook surfaced eleven items a session, four were real, and by week three you stopped opening the review page (the Coverity/Tricorder cliff). The fix is upstream: an explicit [HITL] marker convention in CLAUDE.md so agents register their own questions with high precision, the "not useful" button wired to per-category suppression from day one, and a hard cap of five presented items per sitting.

Confidence: moderate-high on "C or D beats A/B/E alone"; moderate on "D over C" — it depends on Q2 and Q3 below, which only you can answer.

Section 2 · What already exists, as of September 2026

Prior art: everyone asks, nobody keeps a register

Every major agent has converged on a structured "ask the human" tool with nearly the same schema: Claude Code's AskUserQuestion (1–4 questions, 2–4 options, 12-character header, "(Recommended)" first, always an "Other"), Codex's request_user_input (1–3 questions, 2–3 options, a one-sentence trade-off per option, gated to plan mode by default), Cline and Roo's ask_followup_question, HumanLayer's request_human_input with urgency and format. That part of the problem is solved and worth adopting, not rebuilding.

What no one has built is the thing you actually asked for: a persistent, cross-session register of questions the agent guessed at or deferred, with status, owner, evidence, and a path back into the repo's decision record. The closest artefacts are spec-local — spec-kit's ## Clarifications block, compound-engineering's plan-time triage that forces each open question into either a decision or an explicit assumption, BMAD's [ASSUMPTION] tags with blocker-vs-deferred triage, and HumanLayer's rule that a final plan may contain no open questions. Session viewers (a dozen of them) render ~/.claude/projects transcripts; only adr-gen mines them for decisions, and it is a one-star project parsing a format Anthropic documents as unstable.

Seven patterns recur across the survivors: recommendation-first with an escape hatch; rank by impact and cap the count; one question per turn with per-option consequences; answer → write-back → contradiction removal; explicit triage into blocker / assumption / deferred / out-of-scope; ground in evidence before asking; reversibility as an attribute. Only HumanLayer (urgency) and Inngest (timeout as a third outcome) put "how long can this wait" in the question object; no coding-agent tool does.

Section 3 · Failure modes, with the evidence behind each

Why these things die, and the principles that follow

There is no documented postmortem of an abandoned "extract open questions from agent transcripts" tool, so the grounded analogues are the nearest neighbours: self-admitted technical debt mining, static-analysis triage at Google and Coverity, ADR adoption studies, approval-fatigue research, and the CHI/CSCW literature on humans over-relying on AI recommendations. They agree with each other more than you'd expect.

1 · Ask only at one-way doors

Classify every candidate by reversibility × blast radius before it can become a prompt. Two-way doors get auto-decided with a logged default and an undo path — never a question.

Bezos 2015 letter · Claude Code auto mode and Cursor v3.6 both gate prompts on irreversible/destructive/external · Gilbert & Ebert 2002: reversible choices lower satisfaction too

2 · Every surfaced item spends credibility

Target ≥60% action rate and ≤10% "not useful". Wire a dismiss-with-reason button to per-category suppression from day one. Fewer, better items beats coverage.

Tricorder: 10% effective-false-positive bar, analyzers auto-disabled · Coverity: trust collapses past ~30% FP and "the first three reports matter inordinately" · AI review bots muted at 2–3% action rates

3 · Explore before asking

An item is only a question if the answer is not recoverable from the repo, tests, docs or git history. The triage pass attempts resolution first and attaches what it found.

Ambig-SWE (ICLR 2026): Claude models reached equal information gain with ~50% fewer questions by exploring first; implementation-detail questions add little

4 · Decouple "is this a real decision?" from the agent doing the work

A separate classifier with a binary needs-human output and a required rationale, evaluated on a labelled set for both false positives and false negatives.

"Ask or Assume?" intent-agent scaffold: 69.4% resolve rate with well-calibrated asking · Ambig-SWE: agents told to ask over-ask and lose accuracy on well-specified tasks

5 · Use disagreement as the ambiguity detector

Sample several candidate resolutions; agreement → auto-resolve with a logged default; disagreement → candidate item. Don't trust the model's self-report of ambiguity.

ClarifyGPT (FSE 2024): +10 points Pass@1 from code-consistency detection · most models cannot distinguish specified from underspecified tasks

6 · Options and evidence first; recommendation on demand

Reveal the recommendation after a provisional pick or on request. Accept that people rate forcing functions lower; make the step skippable for two-way doors.

Buçinca et al. CSCW 2021: cognitive forcing functions cut overreliance and were least liked · Bansal et al. CHI 2021: explanations raised acceptance regardless of correctness · Fogliato FAccT 2022: concurrent display anchors experts

7 · Every claim verifiable in seconds, or left out

Each trade-off links to a file:line, test, ADR or benchmark. Unverifiable trade-offs are labelled speculation.

Vasconcelos CSCW 2023: explanations help only when they lower verification cost; a salient one reached ~0% overreliance · Coverity: "a not-understood report is labelled false"

8 · Steelman the losers; say why the pick is wrong

A mandatory "why this might be wrong" section from a separate pass with a fixed disagreement stance — but not an always-contrarian judge.

Lord, Lepper & Preston 1984 "consider the opposite" · Chiang IUI 2024 LLM devil's advocate improved appropriate reliance · Smit ICML 2024: always-disagree personas reduced accuracy until tuned

9 · Neutralise framing and order before the model picks

Strip the human's leaning and the prior agent's choice from the prompt; permute option order and majority-vote; judge with a different model family; length-normalise descriptions.

Sharma ICLR 2024: sycophancy shifts answers up to 27 points · tag-question study: ±32 points from "…right?" · Zheng ICLR 2024: position bias survives chain-of-thought

10 · Batch to breakpoints, cap the sitting

Queue items and deliver at task boundaries (plan complete, PR open, end of run) with a bounded delay for high-blast-radius items. About five substantive items or 45 minutes per sitting.

Iqbal & Bailey CHI 2008: breakpoint delivery −20% frustration, −25% reaction time · Cisco/SmartBear review study: effectiveness collapses past 60–90 min · the "hungry judge" decision-fatigue effect is largely an ordering artefact — design for attention, not counts

11 · Record where the code lives, one screen, supersede never edit

The record is a side-effect of the click: context, options, rejected-because, decider, door type, evidence, link to the enacting change. Keep a curated "current decisions" view separate from the append-only log.

Buchgeher 2023: >50% of ADR repos stall at 1–5 records · ICSA 2026: 63% opened already accepted · Kaplan-Moss: RFCs without a decision step default to "no"

12 · Owner, trigger, expiry — or it rots

No open item without an assignee and a resolve-by event. Auto-default unclaimed items and log the default as a decision.

SATD studies: TODOs live 18–173 days median, 20–50% removed by accident, none by process · Coverity alerts fixed in 4 lines but waited a median 96 days

13 · Silence is a valid output

"No human decisions required" is a success, and the eval rewards correct silence.

Ambig-SWE over-asking penalty · habituation halves attention by the second exposure (Anderson CHI 2015, fMRI)

14 · Measure decisions changed, not items extracted

Dashboard: action rate, dismissals by reason, override rate of the recommendation, time-to-decide, post-hoc reversals. A falling action rate is an incident.

Tricorder: "defects corrected, not the number presented" · Atlassian HULA: 82% plan approval but 8% end-to-end — measure the funnel
Section 4 · Verified against code.claude.com docs on 2026-09-12

What Claude Code gives us to build with

Stop · SubagentStop hooks

Receive last_assistant_message, stop_hook_active, transcript_path. Can block and continue the turn (exit 2 or decision: "block"), or inject additionalContext. Eight consecutive blocks cap.

Transcript file may lag; use last_assistant_message for the current turn.

Prompt and agent hook types

type: "prompt" sends the hook input to a fast model for a single-turn JSON decision (30 s default). type: "agent" spawns a subagent that can Read/Grep before deciding (60 s; experimental). Cheap always-on classification.

PreToolUse · defer

permissionDecision: "defer" exits a -p run with stop_reason: "tool_deferred" and deferred_tool_use {id, name, input}; resume with --resume and answer via updatedInput. No timeout; session kept 30 days by default.

Only under -p; only when the turn has a single tool call.

AskUserQuestion

1–4 questions, 2–4 options each, header ≤12 chars, multiSelect, "(Recommended)" first, always an Other. Runs without a permission gate; optional askUserQuestionTimeout.

Removed from every subagent unconditionally; denied in dontAsk and with --permission-prompts none.

Agent SDK canUseTool

Both approvals and AskUserQuestion route to the callback; the app returns updatedInput.answers. TypeScript can request HTML option previews via toolConfig.askUserQuestion.previewFormat.

Python needs streaming mode plus a keep-alive hook.

MCP elicitation

A server can raise a form-mode request with a JSON schema or a URL-mode request; Claude Code shows a dialog. Elicitation/ElicitationResult hooks can intercept or log. _meta["anthropic/requiresUserInteraction"] forces a prompt on every call of a tool.

URL mode is documented with auth as the example.

Skills

Commands are merged into skills. Frontmatter includes disable-model-invocation, user-invocable, allowed-tools, context: fork + agent, hooks (registered when invoked, live for the session), paths, arguments.

Subagents

tools, model, permissionMode, hooks, background, isolation: worktree, memory. Good for grounding in parallel.

Cannot ask the user; return findings to the main conversation.

Plugins

Bundle skills, commands, agents, workflows, hooks, MCP and LSP servers, output styles, themes, background monitors/, settings, and bin/. Distributed through marketplaces.

Headless and structured output

claude -p --output-format json --json-schema validates a structured result; stream-json exposes subagent messages via parent_tool_use_id. --bare for reproducible scripted runs.

Transcripts

JSONL at ~/.claude/projects/<project>/<session>.jsonl; 30-day retention.

Format is internal and changes between versions — build on hooks and -p --resume, not on parsing.

Already shipped, overlapping

Plan mode's clarifying questions; the feature-dev plugin's mandatory clarify phase; TaskCreated/TaskCompleted hooks; plansDirectory (plans persist as files).

No decision registry, no approval state machine, no decision-record artefact type.

Section 5 · The proposal, whichever shape you choose

Proposed design: six stages, one human gate

The pipeline is the same under C, D or E; the shapes differ in where the register lives and which surfaces present. The only stage that needs a person is the fifth. Everything before it exists to make sure that when you are asked, the question is real, the options are grounded, and you can verify the reasoning in seconds.

1

Capture

Three channels, in order of precision.

explicit: [HITL] marker or register_decision tool, required by CLAUDE.md
implicit: Stop/SubagentStop prompt-hook classifier on last_assistant_message; PostToolUse on Write/Edit of .bklg/**, .kb/**, docs/**
backfill: /hitl-scan <path|session>
2

Triage

No human. Try to make the question go away.

recover-from-repo pass (Explore agent)
consistency sampling (N resolutions agree → auto-decide, log default)
dedupe vs last 3–5 .kb decisions
door + blast-radius classification
two-way doors never reach a human
3

Ground

Forked skill or subagent, batched, off the main context.

evidence with file:line and ADR ids
options incl. do-nothing; steelman each
web research where the repo is silent
permuted-order vote; cross-family judge
pre-mortem + "why this might be wrong"
4

Queue

Batch to a breakpoint; cap the sitting.

register row: owner, resolve-by, expiry
deliver at Stop-when-idle, plan accepted, PR opened
≤5 items per sitting; bounded delay for high blast radius
monitors/ nudge: "3 need you"
5

Decide

The one human gate.

interactive: /decide → AskUserQuestion cards
rich: local review page via URL elicitation, or a Cowork artifact like this one
headless: SDK defer loop
recommendation revealed on demand; dismiss-with-reason
answers flow back via updatedInput / additionalContext
6

Record & learn

The click is the record.

MADR 4 + Y-statement → .kb atom via redkiln / kb-ingest, or docs/adr elsewhere
link enacting PR; supersede, never edit
metrics: action rate, override rate, time-to-decide, reversals; auto-suppress noisy categories

The item schema — what makes a question decidable

This is the field set no existing agent question-tool carries. It borrows spec-kit's question rules, RAID's "impact if false", the Rust RFC's resolve-by buckets, ATAM's definition of a risk, and HumanLayer's urgency.

id: D-0042                       # stamped by the CLI under D; by the registry under C
question: "Should the migration audit log be append-only at the storage layer?"   # full interrogative, ends in ?
why_it_matters: one sentence
door: one-way | two-way          # two-way → auto-decided, never presented
blast_radius: file | module | system | external
resolve_by: before-merge | before-release | out-of-scope     # Rust RFC buckets
impact_if_wrong: one sentence
source: { session_id, turn, artifact_path, quote }
evidence: [ file:line, adr:.kb/decisions/…, test:…, url:… ]   # each verifiable in seconds
prior_decisions: [ ids that constrain this one ]
options:
  - { label, summary, good[], bad[], grounded_in[], steelman }   # status-quo option always present
recommendation: { option, rationale, confidence, why_this_might_be_wrong, premortem }
status: candidate | triaged | grounded | queued | decided | deferred | superseded | dismissed
dismiss_reason: not-useful | already-decided | not-my-call | recoverable-from-repo
owner, expires, decider, decided_at, record: .kb/decisions/0042-audit-log-append-only.md

Three design choices worth stating plainly

Make the agent do the capture. Mining transcripts with a classifier is the fallback, not the primary channel. A CLAUDE.md rule that says "when you assume, defer, or cannot decide, emit a [HITL] block with these fields" produces items with high precision because the agent knows what it didn't know. The classifier catches what the agent forgot to declare, and its precision is tracked separately so it can be tightened or switched off.

Two-way doors are decided, logged, and never shown. This is the single biggest lever on volume. A two-way-door item becomes a one-line entry in the decision log with the default taken and a revisit trigger; if it later turns out to matter, it's superseded like any other decision.

The recommendation is earned, not asserted. The grounding pass prompts the model with the human's leaning stripped out, permutes option order across samples, and asks a second model family to judge. What you see is the majority pick plus the strongest reason it's wrong. That is more expensive per item than a single completion, which is another reason the earlier stages exist to keep the count small.

Section 6 · Sequenced to learn before you commit

Roadmap

Estimates are pinned to the lower bound, per your usual pace. Each phase produces a number — the action rate — that tells you whether the next phase is worth building.

Phase 1 · Seed

Plugin skeleton and the habit

  • Plugin repo with skills/hitl-scan, skills/decide, skills/record
  • CLAUDE.md capture convention: the [HITL] block, required for every assumption or deferral
  • Stop/SubagentStop prompt hook → .weighin/inbox.jsonl with dismiss-with-reason
  • /decide uses AskUserQuestion; recommendation appended only when asked
  • /record writes MADR 4 with a Y-statement to .kb/_intake (Redkiln) or docs/adr
  • Adopt spec-kit's question rules verbatim as the skill's rubric
est. one weekend · exit metric: action rate over two weeks of real sessions
Phase 2 · Ground and present

Triage, grounding, the review page

  • agents/triage: recover-from-repo, consistency sampling, door classification, dedupe vs .kb
  • agents/ground: evidence, options with steelmen, permuted vote, pre-mortem, "why wrong"
  • Registry MCP server (SQLite): register, list_pending, decide, dismiss; serves the local review page; URL-mode elicitation from /decide --page
  • Metrics: action rate by capture channel and category, override rate, time-to-decide; auto-suppress under 60%
  • Background monitor: "N items need you" at breakpoints
est. two to three weekends · exit metric: override rate of the recommendation, and whether you open the page unprompted
Phase 3 · Integrate and extend

Redkiln item type, headless loop

  • decision item type with its own process; redkiln new decision is the only writer of state
  • kb-ingest lands decided items as .kb decision atoms; closeout harvests them
  • Companion dashboard "Needs you" column
  • SDK defer loop for -p, cron'd and workflow runs: questions park in the registry and resume on answer
  • Cross-family judge (a second model family, or Codex CLI as second opinion) for one-way doors only
est. two weekends after Phase 2 stabilises · exit metric: post-hoc reversals, and items decided per week from headless runs

Adopt, don't build: spec-kit's clarify question rules; MADR 4 and Y-statements as the record format; HumanLayer's question object as the wire shape; Tricorder's "effective false positive" definition as the metric. Don't adopt: transcript-mining tools; multi-agent debate for the recommendation (majority vote over permuted samples does the work); ten-section decision templates.

Four items the grounding pass could not resolve from the evidence, presented as the tool would present two-way-door questions when it is unsure of the default: quick picks, recorded when clicked, changeable later.

Q1two-way door

How much of your agent work runs unattended (headless, cron, workflows) versus at a terminal?

Decides whether the SDK defer loop belongs in Phase 1 or Phase 3. Below a quarter, it can wait.

Q2two-way door

Where should records land outside Redkiln repos?

Inside Redkiln the answer is .kb decision atoms. IQBG client repos need somewhere: docs/adr (MADR, Backstage-readable) or a Weigh-In-owned folder.

Q3two-way door

Is a second model family acceptable as the judge for one-way-door recommendations?

The evidence on self-preference and position bias says yes; your cost and data-handling constraints may say otherwise.

Q4two-way door

Does "Weigh-In" stay as the name?

It's a working codename chosen for what the items are: things that need someone to weigh in. Your other tools have one-word names.
