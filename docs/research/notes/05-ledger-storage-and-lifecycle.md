# Ledger storage and lifecycle for AI-agent open questions and decisions (per-session and per-repo)

Scope note: this file covers storage format, IDs, concurrency, session scoping, lifecycle hygiene and write-back for the HITL question/decision ledger. It does not redesign the item schema from the prior brief (id, question, why_it_matters, door, blast_radius, resolve_by, impact_if_wrong, source{session_id, turn, artifact_path, quote}, evidence, prior_decisions, options, recommendation, status candidate→triaged→grounded→queued→decided/deferred/superseded/dismissed, dismiss_reason, owner, expires, decider, decided_at, record). Ryan's `.kb` conventions (atom kinds and statuses, accepted-decision immutability, `.kb/_intake/` → kb-ingest) are taken from the assignment brief, not from a web source. Research date: 2026-09-26.

## 1. How agent-oriented in-repo trackers store items, and what went wrong

### Takeaway
Every tool that kept agent work items as mutable records in git files ran into the same three problems: sequential IDs colliding across branches or clones, merges that replace a whole record and silently drop one side's edits, and "hot" shared files (a single JSONL or a generated index) that conflict constantly. The field's answers are hash-based IDs, operation or event storage merged in a deterministic order (git-bug), or leaving git files altogether for a versioned database with cell-level merge (beads moved to Dolt in early 2026). Claude Code's own Tasks avoid git entirely: they live outside the repo, keyed to a session or a named list. That design showed its own failure mode in 2026: tasks were stranded when the session ID changed.

### Cited Findings

**steveyegge/beads (bd), the reference design and how it changed**
- The current beads storage is Dolt, and JSONL is no longer the database: "`.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth or a backup." It has two modes. Embedded mode is in-process Dolt at `.beads/embeddeddolt/` with a single writer. Server mode is an external `dolt sql-server` for multiple concurrent writers. Sync runs through `bd dolt push`/`bd dolt pull` against `refs/dolt/data` on the git remote. — [beads README](https://github.com/steveyegge/beads)
- The beads FAQ gives the reasons for Dolt: "Cell-level merge: concurrent changes merge automatically at the field level", and "No separate sync format: `bd dolt push` / `bd dolt pull` move history natively". JSONL is "a passive export, never the database." — [Beads FAQ](https://beads.gascity.com/reference/faq)
- On concurrency, the FAQ says embedded mode "has race conditions with multiple concurrent writers". It recommends switching to server mode (`bd init --server`) when "multiple processes need concurrent write access to the same database." — [Beads FAQ](https://beads.gascity.com/reference/faq)
- On worktrees: "All worktrees in a repository share the same `.beads` workspace; `bd` discovers it from linked worktrees automatically." — [Beads FAQ](https://beads.gascity.com/reference/faq)
- On IDs: "Sequential IDs (`#1`, `#2`) collide the moment two agents or two branches create issues concurrently — both mint the same next number." Hash IDs such as `bd-a1b2` start at 3 characters and grow as the database grows, holding the collision probability at a fixed threshold. Hierarchical children use the form `bd-a3f8e9.1`, up to three levels deep. — [Beads FAQ](https://beads.gascity.com/reference/faq); [beads README](https://github.com/steveyegge/beads)
- The earlier design (2025) used three layers: git as the "Historical Source of Truth", `issues.jsonl` as the "Operational Source of Truth", and SQLite `beads.db` as "Fast Queries / Derived State". Its rationale: "Binary database files create merge conflicts that are nearly impossible to resolve", pure JSONL is "slow for complex queries", and an "Append-only format minimizes Git merge conflicts". This page appears stale relative to the current README. — [Beads architecture page (older)](https://steveyegge.github.io/beads/architecture)
- Even in the JSONL era, Yegge reported git trouble: "broken rebases, conflicts that need manual resolution". He was testing a "git worktree-based agent village" that used branches instead of file-locking. — [Yegge, "Beads Best Practices", 2025-11-24](https://steve-yegge.medium.com/beads-best-practices-2db636b9760c)
- The JSONL-era issue tracker shows recurring sync and worktree pain. Titles only, bodies not read: "bd sync often fails recommending running... bd sync" (#532); "Prevent untracked issues.jsonl with `sync-branch` and worktrees" (#797); "Sync-branch mode: Local JSONL repeatedly diverges from worktree/database on Windows" (#1379); "Don't write issues.jsonl when using a remote Dolt database as source of truth" (#4074). — [#532](https://github.com/gastownhall/beads/issues/532), [#797](https://github.com/steveyegge/beads/issues/797), [#1379](https://github.com/steveyegge/beads/issues/1379), [#4074](https://github.com/gastownhall/beads/issues/4074)
- The Dolt switch was contentious. In February 2026 users complained that "Removing SQLight creates a setup dependency issue hell" and that "most community tools for viewing tasks in beads have become non-functional". Migration gaps were reported: events lacked `ORDER BY`, and `issues.metadata`/`thread_id` were not migrated. Maintainers said multiple modes ("embedded mode, server mode, SQLite fallback, and JSONL sync") created testing complexity and risk, and summed it up as "git versions files, Dolt versions rows". Some users stayed on v0.49.6 or forked to beads_rust. — [beads Discussion #1836](https://github.com/steveyegge/beads/discussions/1836)
- Size and decay: "Whenever I get more than about 200 issues I start thinking about cleaning up, and I rarely let it go beyond 500." The stated reason is that agents search `issues.jsonl` directly (with jq), which breaks down past about 25k tokens, roughly 500 issues. `bd cleanup` deletes issues older than N days; Yegge set it to 2 days. Deleted issues remain recoverable from git history. — [Yegge, "Beads Best Practices"](https://steve-yegge.medium.com/beads-best-practices-2db636b9760c)
- Current decay: `bd gc` "Deletes old closed issues, squashes old Dolt commits, and runs Dolt garbage collection"; by default it removes issues closed 90+ days ago. The README describes "Semantic 'memory decay'" that "summarizes old closed tasks to save context window". — [Beads FAQ](https://beads.gascity.com/reference/faq); [beads README](https://github.com/steveyegge/beads)
- Agent-facing affordances: `bd ready` lists "tasks with no open blockers"; `bd update <id> --claim` does an atomic claim (assignee + in_progress); `bd prime` injects context; `bd remember` persists insights. Graph links include `relates-to`, `duplicates`, `supersedes`, `replies-to`. — [beads README](https://github.com/steveyegge/beads); [Beads FAQ](https://beads.gascity.com/reference/faq)
- A feature request exists for "Native sync with Claude Code task lists via CLAUDE_CODE_TASK_LIST_ID" (title only, not read). — [beads #1361](https://github.com/steveyegge/beads/issues/1361)

**beads_rust (SQLite + JSONL fork): a fresh 2026 data-loss lesson**
- In beads_rust 0.6.0, two clones adding a child to the same parent both mint `<parent>.1`, because "child_counters is per-database." After a git merge, `br sync --merge` keeps one child and silently drops the other, along with the losing side's comments on the parent. It reports "Merge complete" with exit 0. The reporter asks for hash suffixes on child IDs, a three-way merge that unions comments by identity rather than replacing whole records, and no silent drops. Opened 2026-09-23. — [beads_rust #512](https://github.com/Dicklesworthstone/beads_rust/issues/512)

**Seeds (June 2026): a beads cousin for deliberation and questions**
- Seeds is "a rhyming, gardening cousin of beads". It tracks "plans, deliberations, questions, half-baked ideas", with question items prefixed `q-` (e.g., `q-c3d4`). It quotes Yegge: "finished issues and future issues don't really belong in Beads." Storage is "a SQLite store underneath, and a JSONL export so the deliberation graph stays git-trackable." It "quietly assumes a very small team", with "no multi-user model, no concurrent-editor story". — [Introducing seeds, 2026-06-10](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)
- Seeds' motivation was that plan files were failing because "the deliberation that went into a plan was being silently overwritten" when agents rewrote them. Its lifecycle rule: "every state transition — resolving, deferring, abandoning — takes a reason." Items can be deferred indefinitely, abandoned with a reason, or reopened "because reality disagreed". Actionable seeds graduate into beads ("Make some beads out of these seeds"). — [Introducing seeds](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)

**Backlog.md**
- Storage is one Markdown file per task in a project-local folder (`backlog/`, `.backlog/`, or custom), with subfolders for tasks, drafts, completed, archive, docs and decisions. IDs use a configurable prefix (`TASK-1`, `BACK-1`). Cross-branch accuracy is handled by `checkActiveBranches`, `remoteOperations` and `activeBranchDays`. The project advises agents to "prefer Backlog.md commands (CLI/MCP/Web) over hand-editing task files". `backlog init` writes agent instructions into AGENTS.md/CLAUDE.md and can configure an MCP server. — [Backlog.md README](https://github.com/MrLesk/Backlog.md)
- Bug: "task create reuses an id already claimed by an archived task". The allocator scans only `tasks/` and `completed/`, not `archive/tasks/` or `drafts/`, so "Nothing warns at create time, and the collision is easy to miss because the two files never sit in the same directory listing." Reported against 1.50.1 and 1.51.0; the fetched summary gave the filing date as 2024, which looks wrong and is unverified. — [Backlog.md #997](https://github.com/MrLesk/Backlog.md/issues/997)

**Folder-as-status and generated-index failures in other in-repo backlogs (2026)**
- Pyrite: a long-lived weekly branch still carried `kb/backlog/x.md` after `dev` had moved it to `kb/backlog/done/x.md`. The merge produced two copies with the same ID. Proposed fixes: the validator should "name which side is stale", and the long-lived branch should "rebase-and-prune moved items as a scripted step." Opened 2026-09-20. — [pyrite #209](https://github.com/pyrite-wiki/pyrite/issues/209)
- cachy-app: agents had to regenerate and commit `docs/backlog/INDEX.md` in every PR, and CI demanded an exact match. That made the index a "hot file" with near-constant conflicts across parallel PRs. The fix moved regeneration to a CI workflow that commits it with `[skip ci]` and retries push races up to 5 times, and told agents not to regenerate it by hand. Opened 2026-09-09; shipped in 1.6.1. — [cachy-app #2864](https://github.com/mydcc/cachy-app/issues/2864)

**git-bug: an operation log stored as git objects, not working-tree files**
- "Instead of storing the final bug data directly, we store a series of edit `Operation`s... a common idea, notably with Operation-based CRDTs." Operation packs are JSON blobs in commits under `refs/<namespace>/<id>`. The entity ID is "the hash of the first `Operation` of the entity"; operation IDs are `hash(json(op))`. Ordering uses Lamport clocks, followed by a lexicographic tiebreak on the OperationPack ID. That gives a deterministic merge across clones with no conflicts. Wall-clock time is used "for display" only. — [git-bug data model](https://github.com/git-bug/git-bug/blob/master/doc/design/data-model.md)

**Taskmaster AI**
- Tasks live in `tasks.json`, organized by tags ("master", feature tags). An `id` is "Unique identifier within the tag context", so IDs are sequential integers per tag. Git-branch-based tag switching is listed as a "Future Enhancement". — [Taskmaster task-structure.md](https://github.com/eyaltoledano/claude-task-master/blob/main/docs/task-structure.md)

**GitHub spec-kit**
- Features live in `specs/NNN-feature-name/` (spec.md, plan.md, tasks.md, research.md, data-model.md, contracts/), with project memory in `.specify/memory`. — [spec-kit README](https://github.com/github/spec-kit)
- `/speckit.clarify` is the closest analog to HITL decision capture. It allows a "Maximum of 5 total questions across the whole session" and chooses them by "(Impact * Uncertainty)". It presents the "recommended option prominently", and the user can accept by answering "yes" or "recommended". Each answer is written into the spec under `## Clarifications`, then `### Session YYYY-MM-DD`, as "- Q: <question> → A: <final answer>". The completion report classifies each area as Resolved, Deferred, Clear or Outstanding. — [spec-kit clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)

**Claude Code Tasks (TaskCreate/TaskUpdate/TaskList/TaskGet)**
- Official docs: "Tasks persist across context compactions". "To share a task list across sessions, set `CLAUDE_CODE_TASK_LIST_ID` to use a named directory in `~/.claude/tasks/`: `CLAUDE_CODE_TASK_LIST_ID=my-project claude`." — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode)
- Hooks `TaskCreated` and `TaskCompleted` fire on every task creation or completion and have no matcher support. — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- Third-party report (2026-09-05, no Claude Code version given): tasks are stored as one JSON file per task in `~/.claude/tasks/<session-id>/`. When the session ID changes (the author cites accepting a plan with clear-context, a compaction restart, and an MCP reconnect), the tools "start reading a brand new, empty folder. The old folder is never consulted, merged or migrated", so `TaskList` returns empty. `claude --resume` keeps the ID. This partly contradicts the official "persist across context compactions" claim, which may refer to in-session compaction; unverified. — [dev.to, "session-ID task store trap"](https://dev.to/milkyway008/your-claude-code-tasks-vanished-but-the-files-are-still-there-the-session-id-task-store-trap-2jij)
- Commentary: "If you use the same `CLAUDE_CODE_TASK_LIST_ID` across different repos, Claude could pick up tasks from repo A while working in repo B". Tasks are "session-level" in `~/.claude/tasks`, while beads is "project-level" in the git repo. — [paddo.dev, From Beads to Tasks](https://paddo.dev/blog/from-beads-to-tasks/)
- Observed directly (not from docs): in this research session's tool schema, `TaskCreate` accepts `subject`, `description`, `activeForm` and a free-form `metadata` object, and `TaskUpdate` can merge metadata. A ledger item ID could be carried in task metadata. Not checked against public docs.

### Inferences
- Taken together, the evidence argues against sequential IDs anywhere items are minted concurrently (sessions, worktrees, clones). That covers ledger item IDs and, through the beads_rust #512 lesson, child or sub-item counters too. Hash or time-ordered random IDs (ULID/UUIDv7-style) are the evidence-backed default. Sequential human numbers such as `adr_id` should be assigned only at a single-writer promotion point, such as kb-ingest on main.
- Whole-record replacement is the root cause of silent loss in beads_rust (#512), Seeds' plan files and pyrite (#209). An append-only per-item event stream, or field-level merge as in Dolt, avoids it.
- Status-by-folder (Backlog.md's completed/archive, pyrite's done/) interacts badly with long-lived branches and ID allocators. Status in data (events or frontmatter) is more merge-robust than status by path.
- Committed generated indexes become hot files (cachy-app). Generate the "current open items" view at read time, or in CI, and gitignore it.
- The size ceiling is real. Agents reading a raw JSONL or folder of items degrade at a few hundred items (Yegge's roughly 500 figure). The query path should read a compact projection, not the raw log.
- Claude Code Tasks are the wrong system of record for this ledger: they are session- or list-keyed, live outside the repo, have no repo awareness, and have a reported stranding bug. They are still a useful in-session work list, and the `TaskCreated` hook could mirror tasks into the ledger.

## 2. Event-sourced, append-only JSONL for a question→decision lifecycle

### Takeaway
An append-only per-item event log with a derived current-state projection is well supported by event-sourcing literature and by git-bug's design. The evidence-backed caveats: `merge=union` is safe only if every line is unique and the reducer is order-independent; idempotency needs stable event IDs; concurrent writers need either separate files per writer or a single serializing writer. Compaction should keep the latest state per item while the raw log stays recoverable. A SQLite or other index is worth adding once query cost matters, typically in the low hundreds of items, and only as a gitignored, rebuildable cache.

### Cited Findings
- Fowler on the core properties. Complete rebuild: "We can discard the application state completely and rebuild it by re-running the events from the event log on an empty application." Temporal query: "We can determine the application state at any point in time." Corrections are new events, not edits ("If we find a past event was incorrect, we can compute the consequences by reversing it"). Snapshots are an optimization: "a faster alternative is to store the current application state". The cost: "Packaging up every change to an application as an event is an interface style that not everyone is comfortable with." — [Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- Compaction semantics (Kafka): "retain the latest value for each message key... while discarding older values". "Ordering of messages is always maintained. Compaction will never reorder messages, just remove some." "The offset for a message never changes." Delete markers (tombstones) are kept for a retention window. The docs name event sourcing as a use case. — [Confluent, Kafka log compaction](https://docs.confluent.io/kafka/design/log_compaction.html)
- Idempotency (EventStoreDB/KurrentDB): "The idempotence check is based on the `EventId` and `stream`." Duplicate appends are acknowledged "but duplicate events are not appended." Caveat: "Idempotence is **not** guaranteed if you use `ExpectedVersion.Any`." Optimistic concurrency uses an expected stream version. — [Kurrent docs, Appending events](https://docs.kurrent.io/clients/tcp/dotnet/21.2/appending)
- Deterministic ordering without trusting clocks (git-bug): Lamport clock per entity, "Each new event uses the highest known clock value plus one"; ties are broken lexicographically by pack ID; timestamps are for display only. — [git-bug data model](https://github.com/git-bug/git-bug/blob/master/doc/design/data-model.md)
- Git's `union` driver: "Run 3-way file level merge for text files, but take lines from both versions, instead of leaving conflict markers. This tends to leave the added lines in the resulting file in random order and the user should verify the result. Do not use this if you do not understand the implications." Custom merge drivers are defined in `.git/config` or `~/.gitconfig`, not in `.gitattributes`, so they are per-clone configuration and do not travel with the repo. `union` is built in and needs no setup. — [git-scm, gitattributes](https://git-scm.com/docs/gitattributes)
- When union is safe (Sept 2026): "Append-only, one record per line, order carries no meaning, and no two records are byte-identical → union is safe." Byte-identical records collapse into one copy during a three-way merge, which silently loses data. "Any file where a line can be rewritten → union is a duplicate-record generator." Hash chains, trailing summaries and JSON arrays also break. — [dev.to/rulestack, Two writers, one append-only ledger](https://dev.to/rulestack/two-writers-one-append-only-ledger-the-git-conflict-one-gitattributes-line-fixed-and-the-files-55j0)
- When union is unsound even for append-only files (2026-09-17). Their reducer (`reduce_last_by_finding_id`) treats physical file order as authority. So "one branch appending `accepted` and another `rejected` for the same `finding_id` merge **cleanly** under union and reduce to `rejected` one way and `accepted` the other." Validation also ran only on the locked append path, never after merge. They landed a test guard that fails if any tracked `.jsonl` is union-merged, and recorded the alternative they declined: a semantic merge driver that needs `git config merge.<name>.driver` in every clone. — [arhugula-harness PR #1563](https://github.com/thestoryportal/arhugula-harness/pull/1563)
- Several other 2026 repos adopted or debated `merge=union` for append-only JSONL ledgers (search-result titles only; not read): e.g., "verify-outcomes.jsonl: mark merge=union in .gitattributes so concurrent Evidence PRs stop re-conflicting" and "Append-only registries conflict on every parallel branch". — [assay #588](https://github.com/medici-finance/assay/issues/588); [headstate #1176](https://github.com/StormKiln/headstate/issues/1176)
- The SQLite-as-derived-cache rationale (beads, 2025): JSONL for git-mergeability, SQLite for "Instant queries" and "Complex filtering and sorting"; never commit the binary DB ("merge conflicts that are nearly impossible to resolve"). — [Beads architecture page (older)](https://steveyegge.github.io/beads/architecture)
- Seeds (2026) uses the same pattern: a SQLite store with a JSONL export for git. — [Introducing seeds](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)
- Concurrent writers on one store: beads' embedded single-writer mode "has race conditions with multiple concurrent writers", so they moved to a server that "handles write serialization". — [Beads FAQ](https://beads.gascity.com/reference/faq)
- Beads' Dolt migration surfaced a concrete projection bug: event reads lacked `ORDER BY`, so ordering was non-deterministic. — [beads Discussion #1836](https://github.com/steveyegge/beads/discussions/1836)

### Inferences
- **Event types.** A minimal set derived from the prior brief's status machine plus the patterns above. Candidate list, not a design ruling:
  - `item.raised`: carries the full initial payload (question, why_it_matters, door, blast_radius, source{session_id, turn, artifact_path, quote}).
  - `item.triaged`, `item.grounded` (evidence and prior_decisions attached), `item.queued`, `item.presented` (records that a human saw it, useful for "was it read" metrics).
  - Terminal events: `item.decided` (decider, decided_at, chosen option, rationale), `item.deferred` (new resolve_by), `item.dismissed` (dismiss_reason), `item.superseded` (by id).
  - `item.defaulted`: a two-way-door auto-default with the default logged. `item.expired`. `item.reopened` (Seeds shows reopen is real).
  - `item.linked`: commit SHA, PR URL or atom path. `record.written`: `.kb` atom path and atom id, i.e., write-back confirmation.
  - Following Seeds, every transition event carries a required `reason`.
- **Envelope.** `event_id` (ULID/UUIDv7: globally unique, roughly time-sortable, never byte-identical), `item_id`, `type`, `ts`, `actor` (human or agent), `session_id`, `repo`/`worktree`/`branch`, and optionally a per-item Lamport counter. Unique `event_id`s make every line distinct, which removes the byte-identical-collapse hazard of union merges.
- **Idempotency.** De-duplicate on `event_id` in the projector. For retries of the same logical action (a hook firing twice, a skill re-run), derive the `event_id` deterministically from (item_id, type, content hash) so a replay is a no-op, mirroring EventStoreDB's EventId dedupe.
- **Order-independence.** The projector must not use physical line order as authority (the arhugula lesson). Order by (item Lamport counter or ts, then event_id), and treat two conflicting terminal events for one item (e.g., `decided` A in one worktree, `dismissed` in another) as an explicit conflict state surfaced to the human, not silently resolved. With that property, `merge=union` on a shared file becomes defensible. Without it, union is a latent corruption source.
- **Concurrent writers across worktrees and sessions.** The simplest merge-safe layout, and my own inference, is one file per writer, e.g., `events/<session_id>.jsonl`. Each Claude Code session appends only to its own file, so git merges only ever add new files and never conflict, and no merge driver is needed. The repo view is the union of all files, folded by `item_id`. Within one worktree, parallel processes appending to the same session file (subagents) still need a lock or a single writer. Whether POSIX O_APPEND gives atomic whole-line appends for small writes was not verified here.
- **Compaction and snapshotting.** Kafka-style "latest per key" is a natural snapshot: a `snapshot.jsonl` or projection with one line per item_id, rebuilt from events. Delete raw events only after the item is terminal and its `.kb` atom is written, as beads `bd gc` does for issues closed 90+ days, and rely on git history for recovery as Yegge does. Because accepted decisions live as immutable `.kb` atoms, the ledger's closed tail can be compacted aggressively without losing the record.
- **When an index is worth it.** A gitignored, rebuildable SQLite (or JSON) projection becomes worthwhile once (a) agents would otherwise read the raw log (roughly 25k tokens / 500 items per Yegge), (b) queries cross items (open items touching path X, prior decisions similar to Y, overdue by resolve_by), or (c) several sessions poll "open in repo" often. Below a few hundred items, a `jq`/script fold of JSONL at read time is enough, and it avoids the tooling fragility beads users hit when community tools broke on a storage change.

### Gaps
- No primary Kleppmann (DDIA) or Greg Young text was fetched. Log-compaction and idempotency claims are sourced from Kafka/Confluent and Kurrent docs instead.
- No benchmark was found for the item count at which JSONL-fold versus SQLite crossover happens for agent-facing CLIs. Yegge's roughly 500-issue figure is about agents reading raw JSONL into context, not CPU time.
- I did not verify atomicity of concurrent `O_APPEND` writes on Linux/macOS/Windows (NTFS) for multi-process appends to one JSONL file.

## 3. Session scoping: session identity in Claude Code and Cowork, and showing "this session's items" vs "the repo's open items"

### Takeaway
Claude Code gives a stable, first-class session identity: `session_id` in every hook payload and `${CLAUDE_SESSION_ID}` in skills. It is preserved on resume and changes on fork, `/branch` and `/clear`. That makes "items raised by this session" a simple filter on `source.session_id`. The harder problems are elsewhere. Transcripts are deleted after 30 days by default, so the `transcript_path` link rots. Worktree sessions are blocked from editing files in the main checkout, and gitignored files do not exist in worktrees, so a "repo-wide" view must live either in git (visible only after merge) or in a location shared outside the worktree. Cowork sessions have their own IDs and on-disk store, but no git repo and a sandboxed cwd, so they need a folder- or project-based scope key instead of a repo key.

### Cited Findings

**Claude Code identity surfaces**
- Common hook input fields: `session_id`, `prompt_id`, `transcript_path` (with the note "written asynchronously, may lag current turn"), `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`, `agent_id` (subagents only), `agent_type`. — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- The `SessionStart` matcher values are "startup", "resume", "clear", "compact", "fork". — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- Skills substitute `${CLAUDE_SESSION_ID}` ("Useful for logging, creating session-specific files, or correlating skill output with sessions") and `${CLAUDE_PROJECT_DIR}` (the same path hooks receive). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Skill dynamic injection `` !`<command>` `` "runs shell commands before the skill content is sent to Claude". Caveats: "A failed command aborts the entire skill invocation"; "Claude Code never runs these commands on your machine when they appear in skills synced from your claude.ai account"; it can be disabled with `"disableSkillShellExecution": true`. Personal skills in `~/.claude/skills` load in "All your projects on this machine, but not Cowork or cloud sessions"; claude.ai-account skills load in Cowork, cloud and signed-in terminal sessions. — [Claude Code skills](https://code.claude.com/docs/en/skills)

**Resume, fork, branch, clear**
- `--fork-session`: "When resuming, create a new session ID instead of reusing the original (use with `--resume` or `--continue`)". This implies a plain resume reuses the original ID. — [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)
- "Sessions created with `/branch` or `--fork-session` get their own session IDs." The `/branch` confirmation "prints two session IDs: the new branch you are now in and the original." "If you resume the same session in two terminals without forking, messages from both interleave into one transcript." — [Claude Code sessions](https://code.claude.com/docs/en/sessions)
- `/clear` starts "fresh with an empty context. Claude Code saves the previous conversation; resume it with `/resume`." — [Claude Code sessions](https://code.claude.com/docs/en/sessions)
- Transcripts are stored "as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`". "The entry format is internal to Claude Code and changes between versions." The "30-day retention" is changed via `cleanupPeriodDays`. A separate `desktopSessionCleanupPeriodDays` covers "Claude Desktop and Cowork transcripts". — [Claude Code sessions](https://code.claude.com/docs/en/sessions)
- `claude --resume <session-id>` looks "in the current project directory and its git worktrees first, then in every other project on this machine". The picker defaults to the current worktree; `Ctrl+W` widens to all worktrees of the repo and `Ctrl+B` filters to the current branch. — [Claude Code sessions](https://code.claude.com/docs/en/sessions)
- PR linkage: `--from-pr` opens "sessions linked to a specific pull request... Sessions are linked automatically when Claude creates the pull request". — [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)
- Sessions have names (`-n`, `/rename`) and a generated title. The default display name (e.g., `my-app-3f`) "isn't a resume handle." — [Claude Code sessions](https://code.claude.com/docs/en/sessions)

**Worktrees**
- `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`. A worktree shares "The repository's `.git` directory", project-scope plugins, and permission approvals; untracked `.claude/skills` are read through from the main checkout. — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- "A worktree is a fresh checkout, so untracked files like `.env`... are not present." Gitignored files are copied only through `.worktreeinclude`. — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- "`${CLAUDE_PROJECT_DIR}` stays put: it still points at the project root where the session started"; "`cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root". — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- Isolation enforcement: "Claude Code blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout". It also blocks Bash whose working directory resolves to the main checkout, and git redirects into it. — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- Cross-session messaging "lets Claude pass findings between the sessions in your worktrees" (linked, not read). — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)

**Claude Code Tasks as a scoping precedent**
- The default scope is per session (`~/.claude/tasks/<session-id>/`, third-party). The opt-in shared scope is `CLAUDE_CODE_TASK_LIST_ID`, which names a directory under `~/.claude/tasks/` (official) and is not repo-aware. — [interactive mode](https://code.claude.com/docs/en/interactive-mode); [dev.to](https://dev.to/milkyway008/your-claude-code-tasks-vanished-but-the-files-are-still-there-the-session-id-task-store-trap-2jij); [paddo.dev](https://paddo.dev/blog/from-beads-to-tasks/)

**Claude desktop / Cowork**
- Cowork local-agent-mode sessions are stored at `~/Library/Application Support/Claude/local-agent-mode-sessions/<account>/<space>/<local_id>/audit.jsonl`. Records carry a snake_case `session_id`. "cwd points inside the session sandbox dir, so project attribution must come from the Cowork space / trusted folder, not from cwd." This is a third-party reverse-engineering note, 2026-07-15; unverified by Anthropic docs. — [llm-wiki #31](https://github.com/AlexanderMakarov/llm-wiki/issues/31)
- Cowork sessions and files "live with your Claude account and go where you go, on any device." Cloud sessions can read and write connected local folders "only while the desktop app is open"; projects give shared knowledge context; "local connectors and plugins that include local MCP servers work through the desktop app only". The article does not mention git. — [Claude Help Center, Cowork on web/desktop/mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)

### Inferences
- **"This session's items"** = filter the projection on `source.session_id == ${CLAUDE_SESSION_ID}` (skill) or on the hook's `session_id`. Because `/branch`, `--fork-session` and `/clear` mint new IDs, store a `parent_session_id` or lineage where known. The `SessionStart` source `fork` or `clear` is the hook moment to record it. Otherwise a forked chat shows none of the questions its parent raised.
- **Rotting transcript links.** With the default 30-day retention and an internal, version-changing format, `source.transcript_path` is a pointer that will break. The prior schema's `source.quote` (verbatim excerpt) plus `artifact_path` is what keeps an item auditable. The ledger should copy the quote, not rely on the transcript.
- **"Repo's open items" across parallel worktrees.** If the ledger is committed inside the working tree, items raised in an unmerged worktree branch are invisible to other worktrees until merge. That may be acceptable, since those questions travel with the PR, but it fails a "live, everything open here" view. If the ledger is gitignored in the main checkout, worktrees do not get it (fresh checkout), and worktree sessions are blocked from `Edit`/`Write` into the main checkout. Hooks and scripts invoked through skill injection may not be subject to the tool-level block, but that is unverified. A location shared by all worktrees, such as git's common dir (`git rev-parse --git-common-dir`), or a user-level store keyed by repo root is the pattern beads uses ("All worktrees... share the same `.beads` workspace").
- **Skill injection is fragile as a query path.** A failing `` !`ledger open` `` aborts the whole skill, and synced claude.ai-account skills (the Cowork path) never run injected commands. So the "show open items" step should degrade gracefully: always exit 0, and include a non-injection fallback such as a script the agent runs through Bash, or an MCP tool.
- **Cowork scope key.** With no git repo and a sandboxed cwd, use a scope of (Cowork project or space, connected-folder path) in place of (repo root, branch). Decided records can still land in a `.kb/` folder inside the connected folder, keeping Ryan's "same `.kb` layout everywhere" rule. The live ledger needs a file location that persists across Cowork sessions: the connected folder, not the session scratch or outputs.

### Gaps
- There is no official Anthropic documentation of Cowork session identity: whether `${CLAUDE_SESSION_ID}` is substituted in Cowork skills, or whether Cowork plugins receive hook payloads with `session_id`. Only third-party observations were found.
- It is unverified whether hook scripts, or Bash writing into `$(git rev-parse --git-common-dir)`, are allowed from an isolated worktree session. The docs describe blocking Edit/Write to main-checkout paths, Bash cwd in the main checkout, and git redirects, but say nothing explicit about writes to the shared `.git` dir by non-git commands.
- I did not confirm whether compaction or an MCP reconnect changes `session_id` (dev.to claim) versus only firing `SessionStart` with source `compact`.

## 4. Lifecycle hygiene: owners, resolve-by and expiry, auto-defaults, dedupe, supersession, commit/PR links, and what makes decision logs get read

### Takeaway
The strongest evidence points the same way. Keep the human queue small and ranked (spec-kit's impact × uncertainty cap of 5), require a reason on every transition (Seeds), and fast-track reversible decisions with a logged default (Bezos' Type 2). Supersede rather than edit (MADR, beads links). Decision logs persist when writing them is a team habit with clear guidelines and code links (ADR studies). But pushing the whole log into agent context files does not pay: AGENTS.md-style files raised cost by more than 20% without improving success. So "read" should mean surfacing the few relevant decisions at the moment of work, not a bigger CLAUDE.md.

### Cited Findings

**Triage, quotas and defaults**
- Bezos on one-way and two-way doors: "Some decisions are consequential and irreversible or nearly irreversible – one-way doors – and these decisions must be made methodically, carefully, slowly..." "But most decisions aren't like that – they are changeable, reversible – they're two-way doors." Applying the heavy process to Type 2 decisions leads to "slowness, unthoughtful risk aversion, failure to experiment sufficiently". — [Amazon 2015 shareholder letter (SEC)](https://www.sec.gov/Archives/edgar/data/1018724/000119312516530910/d168744dex991.htm)
- spec-kit caps human questions at 5 per session, ranked by impact × uncertainty. It leads with the recommendation, accepts "yes"/"recommended", and reports the rest as Deferred or Outstanding rather than dropping them. — [spec-kit clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Seeds: "every state transition — resolving, deferring, abandoning — takes a reason. Both habits leave a trail of why." Items may be "deferred indefinitely" or "abandoned (with a reason)". — [Introducing seeds](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)

**Stale items, decay and ready queues**
- Beads pairs a "ready" queue (`bd ready`: no open blockers) with atomic claim (`--claim`) and time-based decay: `bd gc` removes issues closed 90+ days, and Yegge's `bd cleanup` runs at 2 days. — [Beads FAQ](https://beads.gascity.com/reference/faq); [Yegge best practices](https://steve-yegge.medium.com/beads-best-practices-2db636b9760c)
- Yegge recommends daily `bd doctor` ("diagnoses and automatically fixes a wide range of issues"), and restarting agents per task with "Beads acts as the working memory between sessions." — [Yegge best practices](https://steve-yegge.medium.com/beads-best-practices-2db636b9760c)

**Supersession and dedupe**
- MADR status vocabulary: "{proposed | rejected | accepted | deprecated | … | superseded by ADR-0123". It uses "decision-makers", "consulted" (two-way communication) and "informed" (one-way), plus an optional "Confirmation" section. Files follow `NNNN-title-with-dashes.md`, where "NNNN is a consecutive number". MADR 4.0.0 was released 2024-09-17. — [MADR](https://adr.github.io/madr/)
- Beads link types include `duplicates` and `supersedes`. — [beads README](https://github.com/steveyegge/beads)
- Pyrite shows why dedupe must name the stale side. When two copies share an ID across branches, the validator should say "which side is stale". — [pyrite #209](https://github.com/pyrite-wiki/pyrite/issues/209)

**Linking decisions to enactment**
- Claude Code links a session to the PR automatically when Claude creates it, and `--from-pr` finds sessions by PR. — [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference); [Claude Code sessions](https://code.claude.com/docs/en/sessions)
- The ADR action-research study's guidelines explicitly covered "storage location, code linking, review processes, tagging, and status tracking". — [ECSA 2024 action research (PDF)](https://rebekkaa.github.io/files/2024_ECSA.pdf)

**What makes decision logs get read and sustained**
- The MSR study of GitHub ADRs found that "About 50% of all repositories with ADRs contain just one to five ADRs". Systematic use appears where "recording decisions is a team activity conducted by two or more users over a longer period of time". Adoption is "still low, although... increasing every year". — [Buchgeher et al., JKU summary](https://se.jku.at/using-architecture-decision-records-in-open-source-projects-an-msr-study-on-github/); [IEEE Access 2023](https://ieeexplore.ieee.org/document/10155430/)
- Action research (ECSA 2024) found that "clear guidelines on the content to be documented are crucial". A review step "encouraged cooperation". The hindrances were deciding "whether a change should be considered as an ADD" and discoverability: "seven of nine participants" wanted integration into system documentation, and "Some developers had difficulties integrating the creation of ADRs into their daily workflow." — [ECSA 2024 (PDF)](https://rebekkaa.github.io/files/2024_ECSA.pdf)
- Agent context files study: "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average". This held "across different LLMs, coding agents, and for both LLM-generated and developer-committed context files". "Repository overviews... are not helpful"; context files help mainly with "specifying non-standard coding practices." — [Gloaguen et al., arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- LLMs checking code against ADRs (980 ADRs, 109 repos): "substantial agreement and strong accuracy for explicit, code-inferable decisions", but "Accuracy falls short for implicit or deployment-oriented decisions". — [arXiv 2602.07609](https://arxiv.org/abs/2602.07609)
- Generated committed indexes become merge hot spots, and the working fix was CI-owned regeneration. — [cachy-app #2864](https://github.com/mydcc/cachy-app/issues/2864)

### Inferences
- **Owner.** For a solo founder, `owner` defaults to Ryan. The MADR decision-makers/consulted/informed split is the ready-made extension if IQBG peers (The Bridge) are later asked to weigh in.
- **resolve_by and expiry.** Two triggers are supported by the evidence. A time trigger works like beads decay. An event trigger fires when the item blocks work, as with `bd ready` semantics: an item that blocks a PR or task is "due now". On expiry, a two-way-door item can be auto-defaulted to its `recommendation` with an `item.defaulted` event and a reason (Bezos Type 2 plus Seeds' reason rule). A one-way-door item should escalate, never auto-default.
- **Quota.** Following spec-kit, present at most N items per review (5 is their number), ranked by impact × uncertainty (or blast_radius × door), and report the rest as deferred or outstanding rather than silently dropping them.
- **Dedupe.** Check new candidates against (a) open ledger items and (b) accepted `decision` atoms and ADR ids before queuing. Record the match as `prior_decisions`, or dismiss with reason `duplicate-of:<id>`. Beads' `duplicates` link type is the model.
- **Supersession chain.** Accepted decision atoms are immutable, so a changed mind becomes a new decision atom with `supersedes`, and the old one gets `superseded_by`. This exactly matches MADR's "superseded by ADR-0123" and Ryan's conventions. The ledger item for the new question carries `prior_decisions` pointing to the old atom.
- **Commit and PR link.** Record `item.linked` events with commit SHA and PR URL. Claude Code's automatic session→PR link plus `source.session_id` gives a join from PR to session to items without extra instrumentation. Git trailers such as `Decision: <id>` in commits are a common convention but were not researched here.
- **Getting decisions read.** The AGENTS.md study argues against dumping the decision index into CLAUDE.md, which costs over 20% more tokens for no success gain. Put a one-line pointer in CLAUDE.md, and use a hook to inject only relevant decisions at the moment of work: `SessionStart` for a few open items in scope; `PreToolUse` or `UserPromptSubmit` for decisions whose `source_paths` or `related` touch the files being edited. Write decisions so they are "explicit, code-inferable", since that is where LLM compliance-checking works (arXiv 2602.07609). The human-facing index should be generated at read time or by CI, never committed by agents (cachy-app lesson).

### Gaps
- No empirical study was found measuring whether hook-injected, just-in-time decision surfacing improves agent compliance versus static context files. This is an open question.
- No primary evidence was found on expiry or auto-default policies in decision tools specifically, as opposed to Bezos' general management principle.
- Linking ADRs to commits through git trailers or PR templates was not researched with primary sources.

## 5. ADR and decision-log tooling in 2026, and which features correlate with sustained use

### Takeaway
Classic ADR tooling has largely stagnated. The adr.github.io tooling list still shows most tools supporting only MADR 2.x/3.x, while MADR 4.0.0 shipped in September 2024. The 2026 energy is in LLM-assisted ADR generation, extraction and compliance checking, and in agent trackers (beads, Backlog.md, Seeds) that include decision or deliberation records. The only empirical correlates of sustained use are social and process ones: multiple authors over time, clear guidelines on what warrants a record, review, code linking and discoverability. No study ties a specific tool feature to sustained use.

### Cited Findings
- The ADR tooling catalog lists adr-tools ("bash scripts to manage ADRs in the Nygard format", with ports in C#, Go, Java, Node.js, PHP, Python, PowerShell and Rust). It also lists Log4brains ("nice rendering of ADRs and creation of ADRs in a command line", MADR 2.1.2), ADR Manager (web UI on GitHub, MADR 2.1.2), pyadr (lifecycle CLI "proposal/acceptance/rejection/deprecation/superseding", MADR 2.1.2), dotnet-adr (.NET global tool) and the Backstage ADR plugin ("explore and search ADRs within a backstage based developer portal", MADR 2.1.2 and 3.x). The page lists no AI or agent tools. — [adr.github.io ADR tooling](https://adr.github.io/adr-tooling/)
- MADR 4.0.0 (2024-09-17) added "bare" and "minimal" templates and the decision-makers/consulted/informed fields. — [MADR](https://adr.github.io/madr/)
- A large-scale text-mining study found 4,316 ADRs from 547 projects. "Considered Options... was absent or misplaced in most ADRs"; "Decision Drivers were frequently misplaced"; 64% were existence decisions. The arXiv ID suggests September 2026, but the fetched summary said 2024, so the date is unverified. — [arXiv 2609.07375](https://arxiv.org/html/2609.07375)
- ADR usage on GitHub is "still low" but growing, and about 50% of adopting repos have 1–5 ADRs. Sustained use correlates with multi-person, longer-term activity. "In most repositories the template proposed by Michael Nygard is used." — [Buchgeher et al. (JKU)](https://se.jku.at/using-architecture-decision-records-in-open-source-projects-an-msr-study-on-github/)
- In practice, adoption was helped by a customized template (practitioners asked for "Considered Options" and tags), clear guidelines, and review. It was hindered by unclear criteria for when to write one, scattered documentation, and daily-workflow friction. Recommendations included "standardized tagging and cross-repository search" and "automated publication workflows". — [ECSA 2024 (PDF)](https://rebekkaa.github.io/files/2024_ECSA.pdf)
- 2026 research on LLMs and ADRs: violation detection works for explicit, code-inferable decisions. — [arXiv 2602.07609](https://arxiv.org/abs/2602.07609). Titles found but not read: "Context Matters: Evaluating Context Strategies for Automated ADR Generation Using LLMs" ([arXiv 2604.03826](https://arxiv.org/html/2604.03826v1)); "GADR: Gathering Architecture Decision Records from Meeting Transcriptions" ([arXiv 2608.17694](https://arxiv.org/html/2608.17694)); "Architectural Design Decisions in AI Agent Harnesses" ([arXiv 2604.18071](https://arxiv.org/html/2604.18071v1)).
- Agent trackers with decision surfaces: Backlog.md has a `decisions/` folder and searches "across tasks, docs & decisions" ([Backlog.md](https://github.com/MrLesk/Backlog.md)); Seeds tracks questions and answers with reasoned transitions ([seeds](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)); beads has `supersedes`/`duplicates` links and `bd remember` ([beads](https://github.com/steveyegge/beads)).
- The prior brief (00_prior_weigh-in_brief, 2026-09-12, in this folder) already covered adr-gen (transcript JSONL plus git diff to MADR; 1 star) and noted that its transcript-parsing substrate is fragile.

### Inferences
- Tooling that stayed pinned to older MADR versions, together with the social correlates in the studies, suggests the tool matters less than the ritual. The ledger's job is to lower the cost of the ritual: capture automatically, keep the review queue small, and write the atom automatically. That matches the "Some developers had difficulties integrating the creation of ADRs into their daily workflow" finding.
- The studies' main content gaps (missing Considered Options and Decision Drivers) are exactly what the prior schema's `options`, `why_it_matters` and `evidence` fields capture before the decision. Carrying them into the decision atom should produce better records than hand-written ADRs typically contain.
- Human-readable numbers (`adr_id`, MADR NNNN) are consecutive by design and collide across branches, per the beads FAQ reasoning. Minting them at kb-ingest time on main, a single writer, sidesteps that.

### Gaps
- I found no ICSA 2026 paper specifically on ADR tooling or sustained use. The search surfaced only a lab news page and LLM-ADR arXiv papers. Treat "ICSA 2026 ADR evidence" as not found.
- Notion/Confluence decision-log practices and any 2026 "ADR agent" products were not researched with primary sources.
- There is no quantitative evidence linking specific tool features (rendering site, Backstage search, CLI) to sustained ADR use.
- The current maintenance status of log4brains and adr-tools in 2026 (last release dates) was not verified.

## 6. Options for where the live ledger lives and how items become `open_question` / `decision` atoms (not choosing)

### Takeaway
Three evidence-backed placements fit Ryan's fixed rule that decided records land as `.kb` atoms in every repo:
- **A.** A committed per-session event log inside `.kb`.
- **B.** A tool-owned store shared across worktrees and outside git.
- **C.** Items stored directly as `open_question` atoms.

They trade off along the same axes seen in the evidence: git visibility vs live cross-worktree visibility, merge safety vs simplicity, and fit with the `.kb` schema vs a lifecycle richer than `.kb`'s status enum. Whichever is chosen, promotion to a `decision` atom can go through `.kb/_intake/` and kb-ingest, which already enforces frontmatter validity and accepted-decision immutability.

### Cited Findings
(These are the facts each option leans on. All are cited in sections 1–5.)
- Per-writer or append-only logs avoid merge conflicts only if lines are unique and the fold is order-independent. — [rulestack](https://dev.to/rulestack/two-writers-one-append-only-ledger-the-git-conflict-one-gitattributes-line-fixed-and-the-files-55j0); [arhugula #1563](https://github.com/thestoryportal/arhugula-harness/pull/1563)
- Worktrees are fresh checkouts without gitignored files, and worktree sessions are blocked from editing main-checkout paths. — [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)
- Beads shares one `.beads` workspace across all worktrees. — [Beads FAQ](https://beads.gascity.com/reference/faq)
- Claude Code Tasks are stored outside the repo and scoped by session or list ID, with no repo awareness. — [interactive mode](https://code.claude.com/docs/en/interactive-mode); [paddo.dev](https://paddo.dev/blog/from-beads-to-tasks/)
- Folder-as-status resurrection and sequential-ID reuse have been documented. — [pyrite #209](https://github.com/pyrite-wiki/pyrite/issues/209); [Backlog.md #997](https://github.com/MrLesk/Backlog.md/issues/997); [beads_rust #512](https://github.com/Dicklesworthstone/beads_rust/issues/512)
- Committed generated indexes become hot files. — [cachy-app #2864](https://github.com/mydcc/cachy-app/issues/2864)
- Agents reading raw item stores degrade at a few hundred items. — [Yegge best practices](https://steve-yegge.medium.com/beads-best-practices-2db636b9760c)
- spec-kit records clarifications in the feature spec as dated "Q → A" sessions. — [spec-kit clarify.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)

### Inferences

**Option A: committed event log inside `.kb` (e.g., `.kb/_ledger/events/<session_id>.jsonl` plus gitignored `.kb/_ledger/.cache/`)**
- Shape:
  - One append-only JSONL file per session, holding events `item.raised … item.decided`.
  - A projector folds all files by `item_id` into a gitignored snapshot or SQLite cache.
  - On `item.decided`, the skill writes a draft decision atom (kind `decision`, status `proposed` or `accepted` per Ryan's rule) into `.kb/_intake/`; kb-ingest promotes it to `.kb/decisions/`. `record.written` stores the atom path.
  - Long-lived deferred items can also be emitted as `open_question` atoms through `_intake/` so they appear in `.kb` maps.
- For: versioned, reviewable in PRs, travels with the branch that raised it. The per-session file means merges only add files, so no merge driver or union is needed. Same shape as Redkiln's existing append-only JSONL telemetry. Full replay and temporal query (Fowler).
- Against: items raised in an unmerged worktree are invisible to other worktrees until merge, so the repo-wide "open" view is branch-local. Adds ledger churn to PR diffs. Cowork has no git, so the log is plain files in a connected folder without history. Many small files over time need compaction: delete or roll up terminal items once their atom exists, relying on git history as Yegge does.
- Variant: a single `.kb/_ledger/events.jsonl` with `merge=union`. Defensible only if every line has a unique `event_id` and the projector never trusts file order; otherwise it is exactly the arhugula hazard. A guard test like theirs would enforce the invariant.

**Option B: tool-owned live store outside the working tree, shared by all worktrees; only decided records enter `.kb`**
- Shape: live ledger at a repo-keyed location shared by every worktree. Candidates: under git's common dir (e.g., `<git-common-dir>/hitl-ledger/`, invisible to git history), or under a user or plugin data dir keyed by repo root or remote URL (e.g., `${CLAUDE_PLUGIN_DATA}/ledgers/<repo-key>/`, as Claude Tasks do under `~/.claude/tasks/`). Each writer appends to its own per-session events file; a SQLite or JSON projection lives alongside. Decided items are written as atoms into `.kb/_intake/` in whichever worktree or branch enacted them, then kb-ingested.
- For: the "everything still open here" view is live across parallel worktree sessions instantly (the beads shared-workspace pattern). No PR noise. Works in Cowork by keying on the connected folder or project instead of a repo. Matches Ryan's rule that only decided records must land in `.kb`.
- Against: not versioned or shared across machines or clones; lost on a fresh clone or a new laptop unless exported. The open-question history is invisible to reviewers. Worktree isolation may block tool-level writes to main-checkout or `.git` paths, so writes may need to go through hooks or a helper process (unverified). A user-level store risks the paddo.dev "tasks from repo A in repo B" mix-up unless the key is robust (use the remote URL plus root commit, not the path). Shares the reported Claude Tasks stranding failure mode if keyed on session rather than repo.

**Option C: items are `open_question` atoms directly (e.g., `.kb/_intake/open_questions/<hash-id>.md` or `.kb/open_questions/<hash-id>.md`)**
- Shape: each item is a markdown atom with YAML frontmatter (`kind: open_question`), holding the prior schema's fields in frontmatter or body. Status changes are frontmatter edits. On decision, a new `decision` atom is created with `related`/`depends_on` pointing to the question, and the question moves to `withdrawn`/`superseded` or is kept as the answered record. This is spec-kit's "Q → A" inside the artifact, generalized to atoms.
- For: one format, human-readable, greppable, and already understood by kb-ingest and `.kb` maps. No separate projector. Git history is the event log. Closest to Backlog.md's proven file-per-item model.
- Against:
  - In-place frontmatter edits reintroduce whole-record conflicts when two branches touch the same item (the beads_rust #512 and Seeds overwrite class of bugs).
  - `.kb`'s status enum (draft | proposed | accepted | superseded | withdrawn) is coarser than the ledger lifecycle (candidate→triaged→grounded→queued→decided/deferred/superseded/dismissed). It needs either a mapping (e.g., candidate/triaged/grounded/queued → draft/proposed; dismissed → withdrawn; decided → decision atom `accepted` plus question `superseded`) or an extra `ledger_status` field.
  - Folder-as-status must be avoided (pyrite), and IDs must be hash-based (Backlog.md #997).
  - Per-session views need `source.session_id` in frontmatter plus a scan, which hits the agent-reading ceiling at a few hundred items unless a cache is added.
  - Many low-stakes candidate items would pollute the knowledge base unless kept in `_intake/` until triaged.

**Mapping notes common to all options (inference)**
- Decision atom frontmatter can carry lineage back to the ledger: `source_paths` for the artifact, `related` for the item id(s), `supersedes` for the prior decision, `reversibility` mapped from `door` (one-way → low reversibility, two-way → high), and `phase`. Mint `adr_id` at kb-ingest on main to avoid sequential-ID collisions.
- Because accepted decisions are immutable, a changed mind is a new ledger item whose `prior_decisions` points at the accepted atom; its decision atom `supersedes` it.
- A generated `.kb` index of current decisions should be built at read time or by CI, not committed by agents (cachy-app).

### Gaps
- No tool was found that implements exactly option A (per-session event files committed alongside a knowledge base). Its merge-safety rests on git semantics (new files never conflict) and on inference, not on a published case study.
- Behavior of worktree isolation for writes to `$(git rev-parse --git-common-dir)` or user-level dirs from hooks and skill-injected commands is unverified. This is critical for option B.
- There is no evidence on how kb-ingest (Redkiln) handles `open_question` atoms whose status changes frequently. Its dedupe (MERGE-AND-LINK) and immutability checks were designed for knowledge atoms, not a live queue. This should be checked against the Redkiln codebase.
- Cowork: I found no official documentation of a durable per-project file location (other than connected folders) or of whether session IDs are exposed to skills there.
