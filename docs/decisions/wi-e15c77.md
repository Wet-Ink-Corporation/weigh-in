# Should Redkiln's .kb contract reserve .kb/_ledger/ and accept Weigh-In's intake keys in slice 1?

## Context and problem statement

Decides whether every repo has one .kb footprint from day one, and whether the later native decision type is a mapping or a migration.

Door: two-way. A contract note and a kb-ingest change; both can be revised.

Timing: Decide now. Waiting for slice 3 adds a migration of every ledger written in the meantime.

Resolve by: before slice 1 ships.

Evidence:

- [src/store/validate-kb.ts:84] validate --kb already skips _-prefixed directories, so .kb/_ledger/ is invisible to atom validation today.
- [src/schema/kb.ts:61] KbFrontmatter is .passthrough(), so Weigh-In keys such as weighin_item, door and flip_condition survive validation without a schema change.
- [src/schema/kb.ts:8] The schema comment already names tracks and resolution_ref as keys seen on open_question atoms.
- [settled · Q2] Same .kb layout everywhere.
- [gap] How kb-ingest handles open_question atoms whose status changes often is unverified.

## Considered options

### A. Yes: reserve it and teach kb-ingest now (chosen)

Document .kb/_ledger/ as reserved in the .kb README and teach kb-ingest the intake keys in slice 1.

- Holds if: the key names survive slice 1 use without much churn
- If wrong: a key rename touches the README and kb-ingest, not stored atoms (passthrough keeps them valid)

### B. Own .weighin/ folder until slice 3

Keep the ledger outside .kb until the native decision type lands, then move it.

- Holds if: Redkiln's .kb contract is still changing week to week
- If wrong: two footprints per repo, and a migration of every ledger at slice 3

### C. Leave it unspecified until slice 3

Write to .kb/_ledger/ without documenting it; settle the contract with the native type.

- Holds if: nothing in slice 1 depends on the contract
- If wrong: slice 1 writes to an undocumented path that a later kb-ingest may reject
- Evasion flag: Revisit later, with no trigger, default or owner

| Criterion | A | B | C |
|---|---|---|---|
| One .kb footprint from day one | Yes | No | Yes, undocumented |
| Work in slice 1 | About 2 h | None | None |
| Migration at slice 3 | None | Every ledger | Possible |

## Decision outcome

Chosen: **A. Yes: reserve it and teach kb-ingest now**, decided 2026-09-26T18:14:39Z.

The card's recommendation was A (recommended and pre-selected).
Trade-off: You are trading about two hours in slice 1 for no migration later.
What would flip it: kb-ingest turns out to re-ingest an open_question atom on every status change. Then keep open questions in the ledger only and reserve just _ledger/.
Why it might be wrong: The kb-ingest behaviour for frequently changing open_question atoms is unchecked. If it floods _intake, the reservation still stands but the open_question half of the plan needs rework.
Stability: 4 of 4 (Opus pick plus 3 Sonnet samples, each with the option order permuted and the recommendation removed). All samples judged options written by the same author, so this checks order and framing bias, not authorship bias.
