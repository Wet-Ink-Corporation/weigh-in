# Should the ledger's event files (.kb/_ledger/events) be committed to git?

## Context and problem statement

Committed events travel with branches, pull requests and machines. They also put raw agent deliberation into repo history, which a client may not want in theirs.

Door: two-way. You can stop committing at any time, but files already pushed stay in history.

Timing: Decide now. init needs a default, and a per-repo override keeps it cheap to revisit.

Resolve by: before slice 1 ships (weighin init needs a default).

Evidence:

- [src/store/telemetry.ts:4] Redkiln already commits append-only JSONL telemetry, one partition per actor@worktree.
- [src/schema/config.ts:27] auto_stage_telemetry: Redkiln stages those partitions with git add by default.
- [design] The repo view folds events across git worktree list, so open items are visible across worktrees whether or not events are committed.
- [surfaces] Claude Code cloud sessions clone from the remote; an uncommitted ledger does not exist there.

Excerpt, `src/store/telemetry.ts:1`:

```
/**
 * Telemetry sink (spec §4.5, §7, §8, §11).
 *
 * Events are append-only JSONL, one object per line, written to a per-actor /
 * per-worktree partition `${telemetry_dir}/${actor}@${worktree}.jsonl`. Every
 * record is validated against the `Event` schema before it is appended, so the
 * on-disk log always round-trips through the schema.
 */
```

## Considered options

### A. Commit by default; opt out per repo

Every repo commits its event files; a repo that must not carry agent metadata excludes them with .git/info/exclude.

- Holds if: most repos you work in tolerate agent metadata in history
- If wrong: an opted-in client repo carries ledger files in pushed history; removing them needs a history rewrite

### B. Never commit; only decided atoms reach git

Event files stay local and gitignored everywhere; the curated .kb atoms are the only committed record.

- Holds if: you work from one machine and never need open items in a cloud session or on a PR
- If wrong: open items vanish on other machines and in cloud sessions; a lost clone loses the open ledger

### C. Commit in your repos; client repos local by default (chosen)

The same repo class that sets the board mode sets this: your repos commit events, client repos keep them local unless you opt in.

- Holds if: one own/client flag at init describes your repos well enough
- If wrong: client repos lose open items in cloud sessions and across machines until you opt in

| Criterion | A | B | C |
|---|---|---|---|
| Open items follow you across machines | Everywhere | Nowhere | Your repos |
| Raw deliberation in client history | Unless opted out | Never | Only if opted in |
| Settings to reason about | One per exception | None | One flag, shared with the board |

## Decision outcome

Chosen: **C. Commit in your repos; client repos local by default**, decided 2026-09-26T17:56:46Z.

The card's recommendation was C (recommended and pre-selected).
Trade-off: You are trading cloud-session continuity in client repos for keeping raw deliberation out of client history.
What would flip it: Your client engagements treat decision records as a deliverable they want in their repos. Then A.
Why it might be wrong: The decided atoms already land in client repos. If clients are fine with those, the raw events add little extra exposure and C costs you continuity for nothing.
Stability: 4 of 4 (Opus pick plus 3 Sonnet samples, each with the option order permuted and the recommendation removed). All samples judged options written by the same author, so this checks order and framing bias, not authorship bias.

## Later changes

The "commit the event files" half is superseded by [wi-6e2a47](wi-6e2a47.md): open items live in a store under the git common dir in every repo, and decisions reach git as atoms plus a commit trailer. "Client repos keep ledger data local" stays in force.
